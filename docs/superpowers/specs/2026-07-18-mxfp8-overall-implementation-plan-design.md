# DeepSeek V4 MXFP8 整体实施计划

## 1. 总体目标

围绕 DeepSeek V4 建设 MXFP8 低精训练能力，通过三条工作线并行推进，最终达到工程可用并逐步上线。

首版目标如下：

- DeepSeek V4 的 Dense、MoE 主要计算路径支持 MXFP8。
- 目标多机规模下训练稳定。
- 精度满足基于 BF16 基线制定的验收标准。
- 相对 BF16 获得明确、可重复的端到端性能收益。
- 网络能够通过配置决定不同模块是否开启低精。
- 关闭低精配置后执行原有 BF16 路径。
- 具备必要的低精覆盖识别和问题定位能力。

## 2. 建设范围

### 2.1 首版范围

- MindSpeed 仓内独立的 MXFP8 Python Runtime 子模块。
- Runtime 对外接口契约和通用低精上下文管理。
- MindSpore MXFP8 数据类型、scale、量化和矩阵乘能力。
- Dense、MoE 所需的低精正反向能力。
- DeepSeek V4 Dense、MoE 网络适配。
- 普通 TP、EP 等基础分布式路径。
- BF16 基线、低精覆盖范围和网络低精配置。
- 精度、稳定性、性能和多机验证。
- 低精启停验证和逐步上线。

### 2.2 后续增强范围

- All-Gather/MatMul、MatMul/Reduce-Scatter 等通算融合。
- DeepSeek V4 之外的其他网络。
- 更多 FP8 Recipe 和低精场景。
- 权重量化复用等进一步性能优化。

## 3. 总体推进原则

项目由三条工作线并行推进：

1. MindSpeed MXFP8 Runtime。
2. MindSpore MXFP8 算子。
3. DeepSeek V4 网络适配。

三条线各自具有完整目标、工作包和单线进度。Runtime 和算子线可以领先网络线建设后续能力，其交付进度需要满足网络当前接入需求。

项目级汇聚点以网络线为主轴：

```text
Runtime 线   ─────────────────────────────────────→
                 ↘          ↘            ↘
算子线      ─────────────────────────────────────→
                   ↘          ↘            ↘
网络线      ───── Dense ───── MoE ───── 工程可用 ───── 逐步上线
                   ↑          ↑            ↑
                项目汇聚点均定义在网络线上
```

进度管理采用两个口径：

- 单线完成度：分别衡量 Runtime、算子和网络自身的工作进展。
- 项目完成度：以 DeepSeek V4 Dense、MoE、工程可用和逐步上线四个网络汇聚点衡量。

第一阶段是基础能力准备阶段，结束时检查 Runtime 和算子线是否达到 Dense 网络接入条件。网络线在该阶段正常推进自身工作并纳入单线排期，其进度不作为第一阶段的项目退出条件。

## 4. 三方职责边界

### 4.1 Runtime 职责

Runtime 提供通用低精运行能力：

- 提供 MXFP8 上下文管理。
- 定义 Recipe、Tensor 表示和低精算子调度。
- 保证上下文开启时进入 MXFP8 路径。
- 保证上下文关闭时执行原有高精路径。
- 管理量化数据、scale 和临时缓存的生命周期。
- 声明支持的计算路径、并行场景和限制条件。
- 提供低精可用性校验、基本运行状态提示和异常信息。

### 4.2 网络侧职责

网络侧负责决定 Runtime 上下文如何用于 DeepSeek V4：

- 决定 MXFP8 上下文放置在哪些网络代码范围。
- 定义 Dense、MoE 等网络级低精配置。
- 通过网络配置决定对应上下文是否开启。
- 建立 BF16 基线和网络验收标准。
- 提出候选低精覆盖范围。
- 根据 Runtime 契约和算子能力确定实际覆盖范围。
- 完成精度、稳定性和性能验证。
- 通过配置扩大、缩小或关闭低精范围。

### 4.3 MindSpore 算子侧职责

MindSpore 提供 Runtime 所需的真实 MXFP8 计算能力：

- 提供 MXFP8 dtype 和 E8M0 scale 表示。
- 对接已有 ACLNN MXFP8 能力。
- 提供量化、Dense MatMul 和 MoE Grouped MatMul。
- 保证 Shape、dtype、精度和异常语义满足接口约定。
- 支撑网络端到端验证及后续性能增强。

## 5. 低精启停模型

Runtime 提供通用上下文，网络决定上下文的放置位置，并通过网络配置控制上下文是否开启。

```text
网络低精配置
  → 控制目标代码范围中的 MXFP8 上下文
  → 上下文开启：执行 MXFP8 Runtime 和低精算子
  → 上下文关闭：执行原有 BF16 路径
```

首版采用以下状态边界：

- 高精参数是训练语义上的主参数。
- 量化数据和 scale 是 Runtime 在低精执行期间生成的临时表示。
- Checkpoint 延续现有高精训练语义，不保存临时量化表示。
- 低精配置关闭后，网络直接执行原有 BF16 路径。

Dense、MoE 的独立配置由网络定义。Runtime 只提供通用上下文及其开启、关闭语义。

## 6. Runtime 接口契约

Runtime 接口契约在第一阶段制定，是三条线的重要横向依赖。

A0 Runtime 契约与 B0 算子规格并行制定并相互对齐：Runtime 明确所需算子语义，算子侧将底层能力和约束反馈到 Runtime 支持边界。

契约需要明确：

- 低精上下文的调用方式。
- `enabled=True/False` 的执行语义。
- 上下文作用范围和嵌套语义。
- 上下文关闭时的高精执行语义。
- 支持的模块类型和计算路径。
- Dense、MoE 的低精正反向覆盖范围、支持场景和限制条件。
- 支持的 Recipe 和 Tensor 表示。
- 支持的 TP、EP 等并行场景。
- Shape、dtype、设备和版本约束。
- 不支持能力的处理方式。

每项契约能力需要标记为：

- 已实现。
- 首版承诺、正在实现。
- 首版不支持。

网络提出但处于 Runtime 契约外的需求，进入 Runtime 后续扩展范围。

## 7. 工作线 A：MindSpeed MXFP8 Runtime

### A0：接口契约

- 制定并冻结 Runtime 对外接口契约。
- 明确首版已实现、承诺实现和不支持的能力。
- 为网络覆盖范围和 MindSpore 算子规格提供依据。

### A1：独立模块基础能力

- 完成 MXFP8 子模块的职责和依赖边界。
- 建立上下文、Recipe、Tensor 表示和算子调度框架。
- 建立低精可用性校验、基本运行状态提示和模块级测试。

### A2：Dense Runtime

- 支撑 Dense 低精正向、反向和完整训练 step。
- 支撑上下文开启和关闭两种执行路径。
- 支撑网络侧 Dense 接入。

### A3：MoE Runtime

- 支撑 Expert、Grouped MatMul 及相关正反向路径。
- 支撑 Dense 与 MoE 组合运行。
- 支撑网络侧 MoE 接入。

### A4：分布式与工程化

- 支撑普通 TP、EP 等基础分布式路径。
- 完善异常信息和问题定位能力。
- 修正规模训练暴露的状态、缓存和生命周期问题。

### A5：持续优化

- 推进权重量化复用等性能优化。
- 接入通算融合。
- 扩展更多网络和低精场景。

## 8. 工作线 B：MindSpore MXFP8 算子

### B0：规格和底层能力确认

- 固化 dtype、scale、输入输出、Shape、精度和异常约束。
- 确认 ACLNN 接口、版本和依赖条件。
- 建立算子交付顺序。

### B1：基础表示与量化

- 提供 MXFP8 数据表示。
- 提供 E8M0 scale 表示。
- 提供单方向、双方向和 MoE 分组量化能力。

### B2：Dense 计算

- 提供 Dense 正反向所需的量化 MatMul。
- 完成代表性 Shape、精度和异常场景验证。

### B3：MoE 计算

- 提供 MXFP8 Grouped MatMul。
- 提供 MoE 正反向所需的量化计算能力。

### B4：首版性能增强

- 根据 DeepSeek V4 端到端性能结果补充必要的梯度累加等融合能力。

### B5：持续优化

- 提供 All-Gather/MatMul、MatMul/Reduce-Scatter 等通算融合能力。

## 9. 工作线 C：DeepSeek V4 网络适配

### C0：建立 BF16 基线

C0 不依赖 Runtime 和算子线。

交付内容：

- 固定代表性网络、数据和训练配置。
- 固定硬件规模、并行策略和软件版本。
- 建立 loss、目标精度和梯度等数值基线。
- 建立吞吐、单步耗时、显存和资源利用率基线。
- 建立短周期和中长周期稳定性基线。
- 固化数据采集及对比方法。

后续精度和性能验收阈值，根据 C0 结果和网络要求评审后冻结。

### C1.1：候选低精覆盖范围

C1.1 可由网络侧独立开展。

交付内容：

- 梳理 DeepSeek V4 主要计算模块和性能热点。
- 提出 Dense、MoE 等候选低精范围。
- 明确 Dense、MoE 正反向的候选覆盖范围。
- 标记保持 BF16/FP32 的模块和状态。
- 确定候选范围的优先级。

C1.1 产出网络侧低精需求清单。

### C1.2：首版实际覆盖范围

C1.2 依赖 A0 Runtime 契约和 B0 算子能力确认。

首版实际覆盖范围按以下方式确定：

```text
网络候选覆盖范围
  ∩ Runtime 契约支持范围
  ∩ MindSpore 算子可用范围
  = 首版实际低精覆盖范围
```

交付内容：

- 首版确认支持的 Dense、MoE 范围。
- Runtime 契约内但算子尚未到位的范围。
- 网络需要但处于 Runtime 契约外的后续需求。
- 保持高精的模块和训练状态。

### C2：网络低精配置与启停控制

C2 依赖 A0 中的通用上下文契约和 C1.2 确认的首版实际覆盖范围。

网络侧负责：

- 在 Dense、MoE 等目标代码范围放置 MXFP8 上下文。
- 定义对应的网络配置参数。
- 建立配置项与上下文覆盖范围的映射关系。
- 设置低精配置默认值。
- 保证分布式任务中所有 rank 使用一致配置。
- 支持分别开启或关闭 Dense、MoE 低精范围。
- 支持关闭全部 MXFP8 配置。

验证内容：

- 配置开启时，目标代码范围进入 MXFP8。
- 配置关闭时，目标代码范围执行原有 BF16 路径。
- Dense、MoE 配置组合符合网络预期。
- 低精覆盖范围外的模块不受配置影响。

### C3：Dense 网络接入

- 将首版确认范围内的 Dense 模块置于 MXFP8 上下文。
- 完成正向、反向和完整训练 step 验证。
- 与 BF16 基线进行短周期精度、显存和性能比较。
- 验证 Dense 低精配置开启和关闭。

### C4：MoE 网络接入

- 接入 Expert 和 Grouped MatMul 低精路径。
- 验证 Dense 与 MoE 组合训练。
- 覆盖主要 TP、EP 组合。
- 验证 Dense、MoE 配置组合。

### C5：工程可用验证

- 扩展到目标多机规模。
- 验证中长周期精度趋势和稳定性。
- 完成端到端性能、显存和资源效率比较。
- 验证低精覆盖识别和问题定位能力。
- 根据实际性能瓶颈确定 B4 的首版范围。

### C6：逐步上线

- 在验证任务中开启 MXFP8。
- 验证通过后在更多任务和更大规模中使用低精配置。
- 持续观察 C5 已确定的精度、稳定性和性能指标。
- 异常时关闭相应低精配置并执行 BF16 路径。
- 达到工程要求后进入稳定使用状态。

## 10. 总体阶段设计

### 阶段一：基础能力准备

三条线同时启动。

Runtime 线：

- 完成 A0、A1。
- 形成 A2 Dense Runtime 基础能力。

算子线：

- 完成 B0。
- 形成 B1、B2 基础能力。

网络线：

- 推进 C0、C1.1。
- A0、B0 明确后推进 C1.2。
- C1.2 明确后推进 C2。

阶段退出条件：

- Runtime 契约和 Dense 基础能力达到网络接入条件。
- MindSpore 量化和 Dense 计算达到网络接入条件。

C0、C1.2、C2 在 Dense 网络汇聚前完成。

### 阶段二：Dense 网络汇聚

网络线完成 C3。

Runtime 和算子线：

- 支撑 Dense 联调和问题闭环。
- 并行推进 A3、B3。

项目汇聚条件：

- DeepSeek V4 Dense 低精路径能够稳定完成训练。
- 目标 Dense 模块实际进入 MXFP8。
- Dense 配置开启和关闭均符合预期。
- 关闭后执行原有 BF16 路径。
- 完成短周期精度、显存和性能比较。

### 阶段三：MoE 网络汇聚

网络线完成 C4。

Runtime 和算子线：

- 完成 A3、B3。
- 并行推进 A4、B4。

项目汇聚条件：

- Dense、MoE 主计算路径均支持 MXFP8。
- Dense 与 MoE 组合运行正常。
- 主要 TP、EP 组合具备功能正确性。
- Dense、MoE 配置组合符合网络预期。
- 完成 MoE 短周期精度和基础性能比较。

### 阶段四：工程可用汇聚

网络线完成 C5。

Runtime 和算子线：

- 完善 A4。
- 修正规模训练暴露的问题。
- 根据端到端结果完成必要的 B4 能力。

项目汇聚条件：

- 目标规模下训练稳定。
- 精度满足基于 C0 冻结的标准。
- 相对 BF16 获得明确、可重复的端到端性能收益。
- 具备低精覆盖识别、日志和问题定位能力。
- 关闭低精后 BF16 行为与基线一致。

### 阶段五：逐步上线汇聚

网络线完成 C6。

Runtime 和算子线：

- 支撑上线期间问题闭环。
- 修复上线阻塞问题。
- 固化版本依赖、能力范围和已知限制。

项目汇聚条件：

- 低精配置在验证任务和扩大范围任务中均生效。
- 所有 rank 使用一致配置。
- Dense、MoE 可以通过网络配置分别开启或关闭。
- 全部 MXFP8 可以关闭。
- 关闭后执行原有 BF16 路径。
- 实际任务持续满足 C5 的精度、稳定性和性能标准。

### 阶段六：持续优化

三条线继续并行：

- Runtime 推进 A5。
- MindSpore 推进 B5。
- 网络侧扩大低精覆盖范围并接入更多网络。

## 11. 关键依赖关系

```text
A0 Runtime 接口契约
  ↔ B0 算子规格与能力确认

A0 + B0
  └─→ C1.2 首版实际覆盖范围

A0 + C1.2
  └─→ C2 网络低精配置与启停控制

A2 + B1/B2 + C0 + C1.2 + C2
  └─→ C3 Dense 网络接入

A3 + B3 + C0 + C1.2 + C2
  └─→ C4 MoE 网络接入

C3 + C4 + A4 + 必要的 B4
  └─→ C5 工程可用验证

C2 + C5
  └─→ C6 逐步上线
```

关键依赖结论：

- C0 BF16 基线不依赖 Runtime 和算子。
- C1.1 候选覆盖范围不依赖 Runtime 和算子。
- C1.2 实际覆盖范围依赖 Runtime 契约和算子能力。
- C2 依赖 Runtime 通用上下文契约和首版实际覆盖范围。
- Dense、MoE 独立控制由网络通过配置和上下文放置实现。
- 第一阶段结束不对网络线设置项目级要求。
- 后续项目级汇聚点全部以网络结果为主轴。

## 12. 交付与验收标准

### 12.1 阶段一验收

Runtime 线：

- 接口契约已冻结。
- 独立模块边界清晰。
- Dense Runtime 基础能力通过单线验证。

算子线：

- 算子规格和 ACLNN 依赖明确。
- MXFP8 基础表示、量化和 Dense 计算通过单线验证。

### 12.2 Dense 汇聚验收

- 完成 Dense 正向、反向和完整训练 step。
- 实际低精覆盖与 C1.2 一致。
- Dense 配置开启和关闭有效。
- 短周期精度结果满足阶段目标。
- 形成初步性能和显存对比结果。

### 12.3 MoE 汇聚验收

- 完成 MoE 正向、反向和训练验证。
- Dense、MoE 组合运行正常。
- 主要 TP、EP 组合验证通过。
- Dense、MoE 配置组合有效。
- 形成 MoE 精度和基础性能结果。

### 12.4 工程可用验收

- 目标多机规模下训练稳定。
- 中长周期精度满足冻结标准。
- 相对 BF16 获得可重复的端到端性能收益。
- 具备覆盖识别、日志和问题定位能力。
- 低精关闭后 BF16 行为与基线一致。

### 12.5 逐步上线验收

- 低精配置在实际任务中稳定生效。
- 扩大任务范围和训练规模后仍满足工程标准。
- 分布式任务中配置保持一致。
- 异常时能够关闭低精配置并执行 BF16 路径。

## 13. 排期与进度管理

### 13.1 三条线分别排期

每条线分别拆分方案与契约、能力建设、单线测试、网络联调、问题修正和阶段验收，并分别统计单线完成度。

### 13.2 网络线定义项目主里程碑

项目整体排期以以下节点为主：

1. Dense 网络汇聚。
2. MoE 网络汇聚。
3. 工程可用。
4. 逐步上线。

Runtime 和算子侧的对应能力应早于网络联调窗口完成，为集成和问题修正预留时间。

### 13.3 固定联调窗口

排期中设置以下联调和验收窗口：

- Dense 首次联调。
- Dense 汇聚验收。
- MoE 首次联调。
- MoE 汇聚验收。
- 多机稳定性验证。
- 性能分析与复验。
- 上线验证。

### 13.4 动态关键路径

每个网络汇聚点的实际阻塞项构成当期关键路径：

- Runtime 能力未到位时，Runtime 进入关键路径。
- 算子能力未到位时，算子线进入关键路径。
- 能力已到位但网络接入未完成时，网络线进入关键路径。
- 功能正确但性能未达标时，瓶颈对应工作进入关键路径。

## 14. 主要风险

### 14.1 Runtime 契约变化

影响：网络覆盖范围、网络配置和算子规格发生连锁调整。

控制方式：

- 第一阶段冻结 A0。
- 契约变更评估三条线影响。
- 首版需求与后续扩展需求分开管理。

### 14.2 ACLNN 能力或版本不满足

影响：MindSpore 算子交付延期或实际覆盖范围收缩。

控制方式：

- B0 尽早确认底层能力。
- 将底层缺口作为外部依赖管理。
- 根据底层能力更新 C1.2。

### 14.3 网络候选范围超出 Runtime 契约

影响：网络期望覆盖能力无法进入首版。

控制方式：

- C1.1 表达网络需求。
- C1.2 确认首版实际支持范围。
- 契约外需求进入 A5。

### 14.4 MoE 路径复杂度

影响：Grouped MatMul、Expert Shape 和 TP/EP 组合扩大联调周期。

控制方式：

- Runtime 和算子线在 Dense 汇聚期间提前推进 MoE。
- 单线测试和网络汇聚测试分别执行。
- 在 MoE 汇聚阶段预留集成和修正时间。

### 14.5 功能正确但性能未达标

影响：基础 MXFP8 可运行，但端到端收益不足。

控制方式：

- C0 建立统一 BF16 基线。
- C3、C4 持续采集性能数据。
- C5 根据端到端瓶颈确定 B4 首版范围。

### 14.6 网络配置不一致

影响：不同模块或不同 rank 使用不一致的低精配置。

控制方式：

- C2 建立统一配置入口。
- 网络启动时统一下发配置。
- C3 至 C6 验证实际覆盖范围和 rank 间一致性。

## 15. 首版完成标准

DeepSeek V4 MXFP8 首版完成需要同时满足：

- Dense、MoE 首版目标范围进入 MXFP8。
- Runtime 和算子能力满足网络实际覆盖需求。
- 目标规模下训练稳定。
- 精度满足基于 BF16 基线冻结的标准。
- 相对 BF16 获得明确、可重复的性能收益。
- 网络可通过配置分别控制 Dense、MoE 低精范围。
- 全部低精关闭后执行原有 BF16 路径。
- 低精覆盖和异常位置能够识别。
- 逐步上线验证通过。
- 首版范围内的阻塞问题完成闭环。
