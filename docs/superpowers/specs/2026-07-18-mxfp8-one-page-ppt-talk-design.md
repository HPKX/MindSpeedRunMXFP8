# DeepSeek V4 MXFP8 单页 PPT 讲演稿设计说明

## 1. 使用场景

- 汇报类型：技术方案汇报。
- 目标时长：约 8 分钟。
- 对应页面：`outputs/DeepSeek_V4_MXFP8_Implementation_Roadmap.pptx` 第 1 页。
- 汇报目标：让听众理解三条工作线的职责边界、跨线依赖、总体阶段设计和工程可用前的性能增强路径，为后续排期和资源安排建立共同口径。

## 2. 核心结论

讲演需要始终围绕以下结论展开：

> MindSpore 算子、MindSpeed Runtime 和 DeepSeek V4 网络适配三线并行推进；实际可运行能力按照“算子 → Runtime → 网络”逐层交付；项目汇聚和阶段验收以网络结果为主轴。

补充结论：

- 第一阶段只检查基础算子和 Dense Runtime 是否达到网络接入条件，不对网络线设置退出要求。
- Dense 和 MoE 是两个逐层交付的网络汇聚点。
- 工程可用不是单纯完成功能接入，还需要完成端到端验证、性能增强和复验。
- 性能增强依次关注通算融合、梯度累加融合、缓存复用及其余优化。
- 通算融合和梯度累加融合由 MindSpore 算子与 Runtime 联合交付；缓存复用及其余优化由 Runtime 交付。

## 3. 讲演结构

采用“先横后纵”的讲述方式：

1. 先横向解释三条工作线及职责边界。
2. 再纵向沿阶段解释 Dense、MoE 两个交付门的逐层依赖。
3. 重点展开工程可用阶段的验证与性能增强闭环。
4. 最后说明逐步上线和持续优化，并回到排期结论。

该顺序与页面阅读路径一致：先看左侧三条工作线，再看顶部六个阶段，随后沿阶段二、三的竖向箭头阅读依赖，最后聚焦阶段四的橙色工程可用卡片。

## 5. 各段讲演设计

### 5.1 开场：说明这页解决什么问题

开场不逐项念页面内容，先告诉听众这页用于回答三个问题：

1. MXFP8 需要哪三条工作线。
2. 三条线在哪些节点发生依赖。
3. 项目如何形成可排期、可验收的阶段路线。

随后给出总判断：三线并行、能力逐层交付、项目以网络结果汇聚。

### 5.2 三条工作线：讲清职责边界

指向页面左侧，从上到下解释：

- MindSpore 算子线负责真实 MXFP8 计算能力，包括基础表示、量化、Dense MatMul、Grouped MatMul 以及后续融合算子。
- MindSpeed Runtime 线负责通用低精运行能力，包括契约、Context、Recipe、Tensor、算子调度和工程支撑。
- DeepSeek V4 网络线负责建立 BF16 基线、确定实际覆盖范围、放置低精上下文、配置启停并完成端到端验收。

强调网络线决定“在哪里开启低精”，Runtime 提供通用上下文，算子提供底层真实计算。

### 5.3 阶段一：解释并行启动和退出条件

沿阶段一从上到下讲述：

- 算子侧确定规格并完成基础表示、量化和 Dense 计算。
- Runtime 同期制定接口契约和框架，并在算子能力到位后验证 Dense Runtime。
- 网络侧同期推进 BF16 基线、候选和实际覆盖范围、Dense/MoE 启停配置。

必须强调页面底部的阶段规则：网络线在第一阶段正常推进，但不作为第一阶段退出条件；第一阶段退出只看基础算子与 Dense Runtime 是否达到网络接入条件。

### 5.4 Dense、MoE 交付门：解释逐层依赖

沿阶段二、三的竖向箭头分别讲述：

```text
基础算子就绪
  → Dense Runtime 就绪
  → Dense 网络汇聚

MoE 算子就绪
  → MoE Runtime 就绪
  → MoE 网络汇聚
```

说明两个交付门采用相同模式：算子先交付底层能力，Runtime 完成封装和运行验证，网络完成正反向、完整 step、配置启停、精度和性能比较。

补充排期逻辑：Dense 汇聚期间，算子和 Runtime 需要并行提前推进 MoE 能力，避免阶段三完全串行等待。

### 5.5 工程可用：突出验证和性能增强闭环

工程可用是整页的重点，按照以下顺序讲述：

```text
端到端验证与瓶颈定位
  → 通算融合
  → 梯度累加融合
  → 缓存复用及其余优化
  → 端到端复验
  → 工程可用
```

责任归属需要明确：

- 通算融合：MindSpore 算子与 MindSpeed Runtime 联合交付。
- 梯度累加融合：MindSpore 算子与 MindSpeed Runtime 联合交付。
- 缓存复用及其余优化：MindSpeed Runtime 交付。
- 网络侧负责提供端到端数据、定位瓶颈并组织增强后的复验。

验收以目标规模下训练稳定、精度满足 BF16 基线制定的标准，并获得明确、可重复的端到端收益为准。性能增强按端到端结果和既定优先级推进，达到工程指标后收口。

### 5.6 上线与持续优化：说明首版完成后的节奏

逐步上线阶段从验证任务开始，在满足工程指标后扩大任务范围和训练规模。异常时通过网络配置关闭相应低精范围，执行原有 BF16 路径。

持续优化阶段三条线继续并行：算子扩大融合覆盖并增加低精能力，Runtime 进一步优化缓存复用并接入新增算子，网络侧扩大低精覆盖范围并接入更多网络。

### 5.7 收口：回到排期方法

结尾再次强调：

- 三条线分别排期、并行推进。
- 算子能力需要早于 Runtime 验证窗口就绪。
- Runtime 能力需要早于网络联调窗口就绪。
- 项目整体进度以 Dense 汇聚、MoE 汇聚、工程可用和逐步上线四个网络节点衡量。

## 6. 讲演口径

- 采用技术方案语言，突出边界、依赖、阶段和验收，不使用宣传式表述。
- 不展开具体接口签名、算子实现或网络代码修改点。
- 不逐字朗读每张任务卡，只解释任务卡之间的逻辑关系。
- 指图时使用“左侧三条线”“阶段二的竖向箭头”“阶段四的工程可用卡片”“底部阶段规则”等定位语句。
- 关键结论允许重复两次：首次用于建立框架，末尾用于收口。

## 7. 正式讲演稿格式

正式讲演稿按时间段组织，每段包含：

1. 时间范围。
2. 指图提示。
3. 可直接照读的讲述正文。
4. 该段需要强调的关键词。

正文长度控制在约 1800–2200 个中文字符，正常技术汇报语速下约 8 分钟。

## 8. 验收标准

- 覆盖三条工作线、关键依赖节点和六阶段设计。
- 明确第一阶段退出条件。
- 明确 Dense、MoE 逐层交付关系。
- 明确工程可用阶段的性能增强顺序和责任归属。
- 明确逐步上线时通过配置关闭低精并回到 BF16 路径。
- 正文能够直接照读，同时保留自然停顿和指图提示。
- 总时长控制在约 8 分钟。
